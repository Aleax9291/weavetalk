# 织语 WeaveTalk 评估方法论（v5 定型）

> 本文记录评估体系的最终设计与关键决策取舍。核心教训：**对固定评测集逐题打补丁，分数会涨，能力不涨。**

## 1. 为什么推翻"逐题修"的迭代方式

v1→v4 的迭代路径：跑评估 → 看失败明细 → 逐题修 → 重跑。通过率从 64.1% 涨到 90.2%，但复盘发现三类问题：

1. **过拟合评测集**：把失败题的同义表述逐个塞进"必含要素"词表（"您承担"→"您来承担"→"自己承担"……），本质是让评测集背答案。用户换个说法（"运费得我自己掏？"）照样挂。
2. **测量噪声当信号**：多道题在无任何相关代码改动的情况下这轮过、下轮挂（如 GM-03/ORD-01/POL-01）。单次采样 + temperature>0 的生成 + judge 单次判定，本身就有 ±5~10% 抖动。追着单次失败修，有相当部分是在追噪声。
3. **"修评测"与"修 agent"混为一谈**：judge 误判（看不到证据数据，把真实统计当编造）和 agent 真错混在一起，分数变化无法归因。

**结论**：如果继续迭代到 v10，大概率能把这套题刷到 100%，但那是过拟合的 100%，换一个问法就露馅。评估体系本身必须先改对。

## 2. 修复分类学：泛化修复 vs 过拟合补丁

对 v1→v5 的全部修复做分类审计，只有前者计入"能力提升"：

| 类别 | 判定标准 | 例子 |
|---|---|---|
| A 泛化修复 | 换任何问法都生效的系统能力 | 同名多规格商品合并进上下文；多意图分句检索；证据外发给 judge 核验；流式空响应重试；待发货订单注入时效政策；套装品类边界与预算硬约束 |
| B 评测基建修复 | 让测量更准确，但不改变 agent | 禁区词否定前缀豁免（"不可以水洗"不命中"可以水洗"）；judge 对照【证据数据】判编造 |
| C 过拟合补丁 | 只对特定问法生效 | inc 同义词逐题追加；针对单题的 prompt 微规则 |

**处置**：A 保留；B 保留但单独记账；C 从通过标准中移除或改写为通用原则。审计后发现 prompt 中的规则基本已是通用原则（如"库存数字照抄检索结果""不推荐时一句带过"），过拟合主要集中在评测数据的 inc 词表——随判定层改造一并失效。

## 3. 判定层设计（v5 起）

### 双层判定

- **确定性层只查硬约束**：意图匹配、转人工触发、禁区词（带否定/数字前缀豁免）。这些是无歧义的客观行为，不存在"换个说法"。
- **语义层全部交给对照证据的 LLM judge**：事实正确性、要点完整性、行为恰当性。judge 输入包含系统确定性聚合的【证据数据】（评价统计/价格/订单快照），回答中的数字必须能在证据中找到出处——这把"幻觉检测"从主观判断变成可核验的比对。

### 为什么 inc 同义词表被废除

子串匹配假设"正确回答必然包含某个 surface form"，这在自然语言里不成立：语义等价的说法是开放集合，逐题追加词表永远追不完，且每追加一条都在把评测集变成背诵材料。语义完整性只能由语义判断（judge + 证据）来判。

## 4. 泛化性验证机制

### Holdout 集（eval_set_holdout.json）

- 与开发集覆盖相同能力点（12 类意图场景），**全部使用全新问法**：改写句式、换场景、换组合（如"被子哪个最便宜"→"三百块以内能买到什么被子"）。
- **使用纪律**：只在终验跑一次，绝不根据 holdout 结果修改 agent 或 holdout 本身。若未通过，分析归因、修复后重建新 holdout——否则 holdout 就退化成第二个开发集。

### 多次采样与稳定性指标

- 开发集每题跑 3 轮，报告两个数：**平均通过率**（能力水平）与**稳定性**（3/3 一致通过的比例，测可靠性）。
- 时过时挂的"抖动题"单独标记——抖动是稳定性 bug，和稳定失败是两类问题，修复路径不同（前者多为生成随机性/边界 prompt，后者多为检索/策略缺陷）。

### 成功标准（重定义）

| 指标 | 目标 | 含义 |
|---|---|---|
| Holdout 通过率 | ≥ 开发集 − 5% | 能力可迁移到没见过的问法 |
| 稳定性（3/3 一致通过） | ≥ 95% | 同一问题多次回答结果一致可靠 |
| 归因分布 | 检索错/理解错 = 0 | 残余失败仅为模型生成抖动，系统工程部分已闭环 |

## 5. 决策留痕

| 决策 | 选 A | 不选 B | 理由 |
|---|---|---|---|
| 语义判定 | LLM judge + 证据核验 | 扩大确定性词表 | 词表是封闭集合，语义是开放集合；词表路线必然导致过拟合 |
| 评测集管理 | 冻结开发集 + 一次性 holdout | 单一评测集持续迭代 | 持续迭代的集合同时承担"训练信号"和"测量工具"两个角色，测量必然失真 |
| 能力指标 | 通过率 + 稳定性双指标 | 单次通过率 | 单次采样无法区分能力缺陷与随机噪声 |
| 失败处理 | 先归因（检索/理解/生成/策略）再修 | 看失败明细逐题修 | 逐题修把"这一题"修好，归因修把"这一类"修好 |

## 6. 终验结果（2026-08-10，v8 定版）

### 数字演进

| 阶段 | 开发集通过率 | 开发集稳定性 | Holdout 通过率 | 说明 |
|---|---|---|---|---|
| v4（逐题修补时代） | 90.2%（单轮） | 未测 | 不存在 | 分数虚高：含过拟合与噪声 |
| v5（判定层改造后） | 95.7%（3轮） | 90.2% | 87.5%（单轮） | holdout 首验暴露 3 类真实缺口 |
| v8（归因类修复后定版） | **96.7%（3轮）** | **93.5%** | **90.8%（3轮）** | holdout 零稳定失败 |

### 结论

1. **泛化成立**：holdout（全部是没见过的问法）90.8%，且**零稳定失败**——40 题中没有一道是"换了问法就必然挂"的能力空洞。开发集与 holdout 差距 5.9pp，在方法论设定的 ±5~10% 噪声带内。
2. **holdout 的价值被验证**：首轮 holdout 87.5% 暴露出开发集 90%+ 时完全看不见的三类缺口——预算问价误路由去澄清、"焕新床品"误判套装、套装价格幻觉；后续还抓到一个开发集从没暴露的真 bug（2 米床用户被推荐 1.5m 被芯：检索同名去重不看规格）。这些全是"类"级缺陷，按类修复后不再复发。
3. **残余失败主要是测量噪声，不是能力缺陷**：终版开发集唯一稳定失败 GM-06 三轮分别是策略抖动、exc 禁区误伤（"磨毛款夏天会热，直接跳过"命中禁区词"磨毛"）、生成错；holdout 的 7 道抖动题逐案核查几乎全是 judge 对"要点完整性"严格度的随机波动（如答对了"企业抬头需税号"但漏提开票内容明细）。
4. **单轮 holdout 不可信**：同一代码三次单轮 holdout 得分 87.5/95.0/85.0——±5pp 纯噪声。holdout 也必须多轮采样，这是终验过程本身学到的一条。

### 已知残余风险（诚实清单）

- **套装/多数字场景的生成 grounding**：价格单位换算、好评率张冠李戴、折扣算术仍有偶发错误（GM-04/GM-06 类）。prompt 纪律已加码但无法归零——根治方向是结构化输出（计算交给代码）或生成后 GroundingGuard 校验重生成。
- **judge 严格度漂移**：语义判定对"要点完整性"的尺度随 run 波动，是当前最大的测量误差源。下一步：judge 多投票 + 人工抽检校准一致率。
- **holdout 维护成本**：每次按类修复涉及的能力点需重写新问法，长期需要半自动化的问法变异生成。

### 给"做到 v10 能不能 100%"的最终回答

不能，也不该。残余 ~3-9pp 是 LLM 生成抖动与 judge 噪声的叠加，在固定评测集上继续修只会把噪声当信号过拟合。能力的真实边界由 holdout 零稳定失败来界定：**没见过的问题不会稳定地错，只会在测量噪声带内偶发地错**——这是这个项目能给出的最诚实的答案。
